# Divino Bitcoin — Security Invariants

**Status:** `CURRENT — reconciled by WALLET-FOUNDATION-001`

These entries distinguish permanent product foundation from current maturity, acceptance evidence, project hygiene, and workflow controls. This file remains a traceability index, not an independent source of new security policy. A classification change is an amendment to interpretation, not deletion of inherited history.

## Status vocabulary

| Status | Meaning |
|---|---|
| `BASELINE_INHERITED` | Restates a source-backed constraint already present in the declared public baseline; this file does not create it |
| `PROPOSED` | Added or materially clarified by the Project Brain revision; not active until explicitly accepted |
| `RECLASSIFIED_BY_WF_001` | Inherited wording remains traceable, but its category or operational interpretation was amended by `WALLET-FOUNDATION-001` |
| `UNKNOWN/BLOCKED` | Sources conflict, evidence is missing, or reconciliation is required; preserve the block |

## Categories

| Category | Meaning |
|---|---|
| `FOUNDATION` | Permanent property of a genuinely self-custodial wallet; it cannot be relaxed for speed, automation, convenience, or release pressure. |
| `ACCEPTANCE` | Evidence or technical precondition required before accepting secrets, economic value, a release, or a sensitive capability; it may be developed and tested before it is satisfied. |
| `MATURITY` | Current product stage or enabled-surface boundary; it can block use or release without blocking engineering toward the next stage. |
| `HYGIENE` | Privacy, supply-chain, publication, or communication control; important and enforceable, but not part of the custody contract. |
| `WORKFLOW` | Record, delegation, synchronization, or review coordination; it cannot authorize a wallet capability. |
| `MIXED` | Inherited wording contains more than one category and is split by the disposition below. |

## Reconciliation rule and technical boundary

A `MATURITY` or `ACCEPTANCE` status does not authorize a capability. It means only that the project may implement and test toward the next state while the current build remains unable to use the capability in production. A `FOUNDATION` invariant remains binding during development, laboratory testing, release preparation, and operation. Before accepting a wallet-sensitive capability, the active technical decision must name the threat-model controls, negative tests, evidence, review scope, rollback and residual risk. Laboratory tests use disposable material and Signet or synthetic fixtures; they must never be described as customer recovery or production custody.

This file indexes invariants and related controls. It does not decide PSBT design, BIP test isolation, authentication logging, signer architecture, network profiles, native-vault implementation, user-secret recovery, or Lightning recovery. Each requires its own decision ID, threat-model analysis, evidence, review and gate process. `WALLET-FOUNDATION-001` permits implementation toward those decisions while keeping acceptance, release, economic use and foundation changes gated.
