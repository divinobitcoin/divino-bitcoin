## Problem

Conversations across different platforms are not shared memory. Decisions, review findings, evidence, and blockers can therefore become difficult to locate, easy to misremember, or disconnected from the code and public documentation. The project needs a durable, inspectable record that does not depend on any particular AI platform.

## Proposed decision

Adopt GitHub as the project’s **versioned official record** for approved public knowledge, while treating chats as working space and uncommitted notes as drafts. Begin with a minimal six-file Project Brain package:

- [`docs/project/CURRENT_STATE.md`](../project/CURRENT_STATE.md) for the human-readable baseline and immediate boundaries;
- [`docs/project/SECURITY_INVARIANTS.md`](../project/SECURITY_INVARIANTS.md) for non-negotiable security constraints;
- [`docs/project/AI_PROTOCOL.md`](../project/AI_PROTOCOL.md) for reading order, knowledge status, roles, impact, handoffs, and escalation;
- [`docs/decisions/DB-001.md`](DB-001.md) for this governance decision;
- [`docs/project/OPEN_QUESTIONS.md`](../project/OPEN_QUESTIONS.md) for unresolved governance and technical questions;
- [`docs/project/STATE.yaml`](../project/STATE.yaml) for a closed, descriptive, machine-readable state.

The package must remain an indexing and synchronization layer. It must not replace the threat model, native-vault ADR, Signet gates, roadmap, security policy, CI, SBOM, or any future independent review. It must not enable a sensitive capability by wording, status field, label, consensus, or automation result.

## Authority and conflict resolution

The six files have distinct natures and authority:

| File | Nature | Authority boundary |
|---|---|---|
| `DB-001.md` | Normative governance decision | Defines the Project Brain process only; it does not decide product architecture or security gates |
| `SECURITY_INVARIANTS.md` | Normative security index | Contains only invariants inherited from traceable approved records; new invariants remain `PROPOSED` until explicitly accepted |
| `AI_PROTOCOL.md` | Normative process protocol | Governs collaboration and escalation; it cannot enable a capability |
| `CURRENT_STATE.md` | Human-readable descriptive snapshot | Never authorizes a capability |
| `STATE.yaml` | Machine-readable descriptive subset of the snapshot | Never authorizes a capability and must remain synchronized with `CURRENT_STATE.md` |
| `OPEN_QUESTIONS.md` | Informative, non-normative register | Records uncertainty and alternatives; it cannot resolve a decision |

A conflict between a Project Brain file and an ADR, the threat model, a security gate, or another normative record is not resolved by choosing the newest file. The conflict must be marked `UNKNOWN/BLOCKED` until an explicit reconciliation decision is recorded. For wallet-product questions, [`WALLET-FOUNDATION-001.md`](WALLET-FOUNDATION-001.md) defines the foundation contract and the technical ADR/threat model define its implementation and evidence. Recency is provenance, not authority.

No status field, YAML value, AI consensus, review count, issue label, CI result, handoff, or commit message can by itself enable a security-sensitive wallet capability or change the wallet foundation. Acceptance of a wallet capability still requires the applicable technical decision, evidence, review and owner decision where required; implementation and laboratory testing within an approved technical decision may proceed without unit confirmation. External workflow actions may be authorized by an explicit category package under GOV-REF-001 and must remain within that package.

`CURRENT_STATE.md` is the human view and `STATE.yaml` is a structured subset of the same snapshot. Divergence between them is a synchronization error; neither representation wins by recency.

## Clarifications and improvements to the original proposal

The repository is an official versioned record, not an infallible authority. Each state assertion must identify its baseline, verification date, source, and uncertainty. `STATE.yaml` is fail-closed and descriptive; no free-form text can authorize a gate.

The project will preserve independent opinions and objections. A future review package may contain separate problem, builder, guardian, reviewer, and final-decision files, but this initial adoption does not create or imply an independent security review.

The Caderno Privado de Fundamentos is excluded from automatic synchronization or publication. Only principles explicitly approved by the owner may be rewritten into public material after removal of personal and third-party context and a separate publication confirmation.

DB-001 does not introduce additional Project-Brain-specific CI governance checks. The CI and dependency-risk controls already present at the declared baseline remain unchanged and outside the implementation scope of this decision. The initial Project Brain package did not introduce issue templates, labels, branch-protection changes, external connectors, automatic synchronization, or platform credentials. GOV-REF-001 is a later owner-approved workflow decision: it permits explicitly delegated categories to use named connectors, accounts and channels within package limits; it does not grant unrestricted access or alter wallet security.

## Alternatives considered

| Alternative | Disposition | Reason |
|---|---|---|
| Keep conversations as the primary memory | Rejected | Cross-platform memory is incomplete and hard to audit |
| Give one AI’s instruction file authority over the others | Rejected | Creates an avoidable single-agent reference point |
| Publish the entire conversation history | Rejected | Exposes private context and does not distinguish facts, hypotheses, or approvals |
| Build full automation and CI enforcement immediately | Deferred | Increases scope and can create false confidence before the record format is proven |
| Use the six-file minimum plus a future context pack | Accepted for now | Preserves a small initial surface while leaving room for a later navigation layer |

## Security and scope conditions

1. The wallet foundation defined by [`WALLET-FOUNDATION-001.md`](WALLET-FOUNDATION-001.md) is the non-negotiable floor: customer control, no secret exfiltration or remote custody, independent recovery, transparent signing, network isolation, fail-safe behavior and non-custodial Lightning cannot be bypassed.
2. The current build remains a local demonstration and Signet is the default development environment. Mainnet, real funds, production signing, user-secret recovery, broadcast, operational endpoints, active Lightning and a functional native vault are not enabled at the current maturity stage; implementation and laboratory testing toward them may proceed under their technical decisions.
3. The native vault remains opaque and fail-closed while sensitive operations are not accepted.
4. No public file may contain a private management address, credential, secret, personal data, real-fund record or unapproved private reflection. Project privacy is a preference and may be revised by the owner; accidental disclosure remains a defect.
5. Public statements must distinguish verified facts, hypotheses, recommendations and blocked capabilities. Public community auditing is a future maturity phase, not a gate for every current sprint.
6. GOV-REF-001 permits autonomous local work and explicitly delegated external categories, including named GitHub, YouTube or community channels, without unit confirmation for each covered operation.
7. A category package must specify scope, account/channel, content/template, validity, limits, evidence, rollback and revocation. It does not expand by implication to another capability.
8. This decision does not authorize wallet-capability use, custody, signing, recovery, broadcast, Lightning, Mainnet or funds. It coordinates workflow only; product foundation and technical acceptance remain governed by WALLET-FOUNDATION-001 and their own ADRs/gates.

## Technical-scope boundary

DB-001 is strictly about project memory, governance records, collaboration protocol, and state synchronization. Technical decisions about PSBT, BIP test isolation, authentication logs, signers, network profiles, the native vault, recovery, or Lightning require separate decision IDs and their own threat-model, evidence, review, and gate process.
